# Astvard — записки для агента

Прочитай это до того, как что-то менять. Здесь то, чего не видно в коде:
почему сделано именно так и на чём тут уже обжигались.

## Что в репозитории

Две почти не связанные вещи под одной крышей:

| Часть | Что это | На чём |
|---|---|---|
| `server.js` `src/` `client/` `public/` `db.js` | портал astvard.online: публичный сайт, кабинет, админка, вайтлист, статус серверов | Node.js без фреймворков, Postgres |
| `valheim-mod/` | мод Valheim: админ-панель в игре, шаблоны построек, рельеф, автоматизация | C# net472, BepInEx + Jötunn |

**Портал — это админ-панель хозяина** (`vanilla-admin-panel`), перенесённая сюда
12.09.2026 целиком: свой сервер на `node:http`, схема в `db/schema.sql`,
сессии в базе, роли `Superadmin/Admin/User`, статьи, медиатека, уведомления, логи,
2FA. Прежний портал (`backend/`, `frontend/` и прежний `db/`) снесён; он остался
в истории git, и оттуда же перенесены наши три вещи — вход через Steam, вайтлист и
статус серверов. Модули панели про электрику (сотрудники, инструмент, автопарк,
заявления, учёт времени, каталог) снесены целиком 19.09.2026 — подробности в разделе
«Незакрытое».

Общего кода у них нет — собираются, запускаются и ломаются порознь.
`deploy/` — установка на VPS: сайт, nginx, Valheim в Docker; как и почему — `deploy/README.md`.
`placeholder/` — заглушка сайта и её конфиг nginx; на VPS с 11.09.2026 её сменил сайт.
`valheim-mod/decompiled_*.cs` — куски игры для справки, в git не лежат.

## Как поднять

```bash
docker compose up -d   # Postgres на 127.0.0.1:5432, встаёт и после перезагрузки
npm install            # ничего нативного: pg — обычный JavaScript
npm start              # сайт на :3001, читает .env из корня
```

База — Postgres из `docker-compose.yml`: роль и база `astvard`, пароль `astvard_dev`
или `POSTGRES_PASSWORD` из `.env`. Схему панель накатывает сама при старте из
`db/schema.sql` и сама заводит настройки и демо-аккаунты на чистой базе. Тестам нужна
своя база рядом, заводится один раз:

```bash
docker exec astvard-postgres createdb -U astvard astvard_test
npm test
```

Агенту с браузерной панелью удобнее поднимать сайт через `preview_start`
по имени `astvard-backend` — запись уже лежит в `.claude/launch.json`,
тогда логи читаются штатно, а не из перехваченного вывода.

Игровой сервер — только через свой bat, из его же папки. Процесс надо **отцепить**:
команда агента завершается вместе с вызовом и утащила бы сервер за собой. И сразу
`-WindowStyle Hidden` — иначе на рабочем столе хозяина машины открывается окно cmd,
которое там никому не нужно: весь вывод и так пишется в `-logFile`.

**Сервер, запущенный из Claude, живёт, пока живёт приложение Claude.** Claude Desktop —
пакет MSIX, и всё, что его инструменты запускают, даже через `Start-Process`, остаётся в
его контейнере. 11.09.2026 в 02:08 приложение само обновилось, Windows закрыла процессы
пакета, и сервер умер без `OnApplicationQuit`: лог оборвался на плановой строке в 02:01,
в журнале Windows рядом — «cmd.exe was closed» и установка пакета Claude. Мир уцелел
только потому, что никто не играл: последнее сохранение было за семь минут до этого.
То же будет при закрытии приложения.

**И так и задумано: этот сервер — отладочный.** Хозяин решил 11.09.2026: ни планировщика,
ни автозапуска не нужно — агент поднимает и останавливает сервер сам, а настоящий сервер
будет на VPS. Значит, в начале работы с модом проверь, жив ли `valheim_server`, и если
нет — подними его, как написано ниже; упавший вместе с Claude сервер — не авария.

**Запускать из PowerShell, не из Bash.** Сервер, поднятый из Bash через
`powershell -c "Start-Process …"`, потом глух к Ctrl+C: `send_ctrl_c.ps1` отрабатывает с
кодом 0, а игра не выходит. Похоже, запрет Ctrl+C наследуется от оболочки Bash через всю
цепочку до `valheim_server.exe`. Проверено 10.09.2026 на двух экземплярах подряд:
поднятый из Bash простоял минуту после сигнала и был убит; поднятый той же командой из
PowerShell вышел за 4.4 с и записал сохранение № 19.

```powershell
Start-Process 'C:\Games\steamapps\common\Valheim dedicated server\start_astvard.bat' -WorkingDirectory 'C:\Games\steamapps\common\Valheim dedicated server' -WindowStyle Hidden
```

**Останавливать — только Ctrl+C в его консоль.** Тогда игра пишет мир на выходе: в логе
`Game - OnApplicationQuit`, `ZNet Shutdown`, `World save (5/5) done`, а в
`worlds_local\AstwardWorld` появляется следующий номер `_main.N.*`. Убитый процесс теряет
всё после последнего автосохранения (`-saveinterval 900`, то есть до 15 минут). Окно
скрыто, поэтому Ctrl+C нажимает `valheim-mod/server/send_ctrl_c.ps1`, и только отдельным
скрытым процессом: ему приходится бросить свою консоль и подцепиться к консоли сервера.
`cmd.exe` от bat после этого остаётся висеть в скрытом окне (судя по всему, на «Terminate
batch job (Y/N)?») — его добить, но **только после того, как сервер вышел**: убитый
раньше `cmd.exe` сервер не остановит. Если за минуту сервер не вышел, он глух к Ctrl+C
(см. выше про Bash) — тогда сверить время последнего `World save (5/5) done` с последним
действием игроков и только потом убивать. Проверено 10.09.2026: сервер вышел за 2.6 с и
записал сохранение № 17. Из корня репозитория:

```powershell
$server = (Get-Process valheim_server).Id
Start-Process powershell -ArgumentList '-NoProfile','-ExecutionPolicy','Bypass','-File',"$PWD\valheim-mod\server\send_ctrl_c.ps1",'-TargetPid',$server -WindowStyle Hidden -Wait
# дождаться, пока valheim_server исчезнет, и проверить в логе World save (5/5) done, затем:
Get-CimInstance Win32_Process -Filter "Name='cmd.exe'" | Where-Object CommandLine -match 'start_astvard' | ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
```

Проверка, что всё действительно живо (не верь тому, что процесс просто есть):

```bash
curl -s http://127.0.0.1:3001/api/health          # ждём {"status":"ok","db":"ok"}
netstat -ano -p UDP | grep :2456                  # игровой сервер слушает
tail -5 "/c/Games/valheim-servers/astvard/logs/astvard_server.log"
```

В логе ждём `Valheim version: ...` и `Game server connected`. Смотреть надо именно
в этот файл, а не в `Player.log`: для Unity клиент и сервер оба «IronGate/Valheim»,
пишут по одному пути и отбирают его друг у друга — ошибки клиента там легко принять
за серверные. Отсюда и `-logFile` в bat.

**Логов два, и мода в этом нет.** `-logFile` перехватывает только вывод Unity, включая
прелоадер BepInEx. Сам загрузчик после старта пишет к себе, в
`BepInEx\LogOutput.log` внутри папки установки. Строки `Loading [Jotunn]` и
`Loading [AstvardServerMod]` искать надо там, и «мода нет в логе сервера» почти всегда
означает, что смотрели не в тот файл. Второй сервер на этой же установке будет писать
в тот же `LogOutput.log` — когда дойдёт до этого, разводить через `BepInEx.cfg`.

**`Connections N` в логе сервера — не всегда игроки.** Генератор подземелий пишет
свою строку `Connections N` — про проходы между комнатами, рядом с `Available rooms`
и `placed N doors`. Игроков считает только строка вида `Connections N ZDOS:… sent:… recv:…`,
а кто именно зашёл — `Got connection SteamID <число>`.

## Сервер: как он собран и почему именно так

Пересобран 10.09.2026 с нуля. Каждый флаг в `start_astvard.bat` выбран по коду
`assembly_valheim.dll` 1.0.7, а не по вики, и **отсутствие флага — тоже решение**.
Причины расписаны в шапке самого bat; здесь то, что важно помнить снаружи.

- **Сохранения переехали из папки игры** в `C:\Games\valheim-servers\astvard`.
  Обновление или проверка целостности Steam туда не дотянется, и вторая установка
  потом сможет делить этот же бинарник со своим `-savedir`.
- **Вход по вайтлисту, пароля нет.** Пароль игра требует только у публичного сервера,
  а этот `-public 0`. `permittedlist.txt` пустой означает «пускать всех»; список
  включается с первой же строки. Оба списка перечитываются на ходу, примерно раз в
  десять секунд, и выпавшего из вайтлиста кикает сразу. Но **только если файл новее
  прочитанного**: `SyncedList.Load` (в `assembly_utils.dll`) сравнивает время изменения
  файла с последней загрузкой и выходит, если оно не больше. Список, положенный со
  старой датой (`scp -p`, распаковка архива), игра молча не заметит до перезапуска;
  после такого копирования — `touch`. Ошибки чтения там же глотаются пустым `catch`.
  Концы строк неважны: читает `StreamReader.ReadLine()`, ему годятся и `\r\n`, и `\n`.
- **`-public 0` прячет сервер и от A2S.** `ZSteamMatchmaking.RegisterServer` зовёт
  `SteamGameServer.SetAdvertiseServerActive(true)` только для публичного сервера, а без
  этого Steam не отвечает на запросы серверного браузера. Проверено 11.09.2026 на VPS:
  на `A2S_INFO` молчат и 2456, и 2457 — снаружи, с самой машины и по адресу контейнера,
  хотя игра оба порта держит. Поэтому опрос статуса сайта (`backend/protocols/a2s.js`)
  этот сервер не увидит никогда. С 12.09.2026 статус берётся из **его собственного
  лога**: у строки сервера в базе `probe = 'valheim-log'`, разбор — в
  `backend/protocols/valheim-log.js`, путь к файлу — `VALHEIM_LOG_FILE`. Игра пишет
  `Connections N ZDOS:` раз в десять минут, и раньше этим счётчиком всё и
  ограничивалось; с 12.09.2026 состав онлайна собирается из строк входа и выхода
  (`Got connection SteamID`, `Closing socket`), то есть точность мгновенная — см.
  раздел «Незакрытое». «Онлайн» решается свежестью файла по `mtime` (не по времени
  внутри строк — оно в часовом поясе контейнера) и тем, что после последнего
  сердцебиения нет `OnApplicationQuit`/`ZNet Shutdown`.
- **ID пишется как `V_<SteamID64>`, и только так.** `ZNet.ListContainsId` прогоняет
  пришедший с сокета ID через `PlatformUserID.FilterPlatformUserID`, где платформа
  `Steam` превращается в префикс `V`, а последняя ветка **присваивает** флаг совпадения,
  а не добавляет его — так что голая цифра и `Steam_…`, проверенные до неё, выбрасываются.
  В `adminlist.txt` при этом стоит и `Steam_…`: `ZNet.PlayerIsAdmin` сравнивает сырым,
  и от него зависит кнопка кика в игровом списке игроков.
- **`-crossplay` не включён намеренно.** Он меняет весь транспорт на PlayFab Party:
  слушающего сокета нет, вход по IP превращается в поиск по лобби и отказывается от
  приватных адресов, серверная информация для A2S не публикуется вовсе, а личность пира
  приходит полем, которое написал сам клиент, вместо тикета, проверенного через
  `BeginAuthSession`. Для Steam-компании на белом IP это всё минусы без единого плюса.
- **`-preset` не передаётся.** Пресет вписывается в мир **при каждом старте** и остаётся
  там до `-resetmodifiers`. Старый мир до сих пор носит `nobuildcost`, `passivemobs` и
  `eventrate 0` от одного запуска с `-preset Hammer`.
- **Сид командной строкой не задаётся, флага нет.** Мир, созданный сервером, получает
  десять случайных символов из `World.GenerateSeed()`. Чтобы выбрать свой — создать мир
  клиентом и положить папку в `worlds_local`. Личность мира — **имя папки**:
  `SaveSystem.GetChunkedSaveName` это буквально
  `Path.GetFileName(Path.GetDirectoryName(path))`. Файлы внутри не переименовывать.
- **Кэш биомов привязан к имени мира** (`cache\<Мир>_biomedatacache.bin`). Подкладывая
  чужую карту под то же имя, кэш надо удалить, иначе он будет принят как свой.

Старый мир не удалён, лежит в
`C:\Games\steamapps\common\Valheim dedicated server\saves.removed-20260910-0052`.
Прежний bat — рядом, как `start_astvard.bat.old`.

**Клиент вычищен до ванили** был 09.09.2026 и с тех пор BepInEx на нём поставлен заново.
Содержимое старого `BepInEx/config` лежит в `.backups/valheim-client-bepinex-config/` —
33 файла, сверено хешами. Там `astvard-templates` с чертежами построек: имена файлов
врут, судить надо по заголовку `#name` внутри (`y.txt` — это база на 751 деталь).

`.env` не в git. Ключи портала: `PORT=3001`; `APP_URL` — абсолютный адрес сайта, на
него Steam возвращает игрока, и этот адрес входит в подпись ответа (из заголовка
`Host` его брать нельзя, его пишет тот, кто стучится): локально
`http://localhost:3001`, на VPS `https://astvard.online`; `POSTGRES_HOST`,
`POSTGRES_PORT`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` — база;
`TRUST_PROXY=true` на VPS — nginx терминирует HTTPS, без этого кука сессии не получит
флаг `Secure`; `VALHEIM_LOG_FILE` — лог игрового сервера для строк с
`probe = 'valheim-log'`; `VALHEIM_MOD_CONFIG` — папка конфигов мода
(`/srv/valheim/server/BepInEx/config`), откуда раздел «Наш сервер» берёт руны и
общие постройки; `VALHEIM_SAVES_DIR` — папка сохранений игрового сервера
(`/srv/valheim/saves`), **единственное место, куда сайт пишет** за своими
пределами: два файла списков доступа; `GAME_LISTS_TOKEN` — токен, по которому мод
игрового сервера забирает списки с `/api/game/lists` (тот же вписывается моду в
`[Сайт] ListsToken`, без токена маршрута нет вовсе); `SUPERADMIN_STEAM_ID` — SteamID64 хозяина: `src/bootstrap.js`
при каждом старте смотрит, есть ли хоть один `Superadmin`, и если нет — заводит или
повышает этот аккаунт, сразу с одобренным вайтлистом и админкой в игре. Пока этот ключ
задан, `db.js` **не создаёт** демо-аккаунты `superadmin/admin/user` с паролем
`1234qwer`: на живом сайте это не вход, а дыра с табличкой. Пароля у хозяина нет
вовсе — вход через Steam.

На VPS есть ещё `POSTGRES_CONTAINER=postgres-shared` — в каком чужом контейнере живёт
наша база; его читают только скрипты в `deploy/`, самой панели он безразличен.

**JWT в панели нет вовсе.** Сессия — случайный токен в куке `session`, строка в таблице
`sessions` и запись в Map. `JWT_SECRET`, если он остался в чьём-то `.env`, — от прежнего
портала, и никто его не читает.

**Миграций нет: `db/schema.sql` накатывается поверх живой базы при каждом старте** и
обязан оставаться идемпотентным. `CREATE TABLE IF NOT EXISTS` пропускает существующую
таблицу целиком, вместе с колонками, поэтому каждая колонка, добавленная после первого
развёртывания, есть в файле **дважды** — в `CREATE TABLE` для чистой базы и отдельным
`ALTER TABLE ... ADD COLUMN IF NOT EXISTS` в хвосте файла. Добавляешь колонку —
добавляй в оба места, иначе на боевой базе её не будет.

Так сделано после того, как миграции панели один раз уже подвели: версия отмечается
выполненной в тот же миг, когда миграция выдана, и падение внутри неё оставило бы работу
несделанной навсегда. Из-за этого в базе не оказалось `notifications.scheduled_at` —
нашлось только при переносе схемы.


## VPS: astvard.online и настоящий сервер

Подняты 11.09.2026. Вход с этой машины — `ssh astvard-vps` (root). **Машина общая**:
чужие PM2-приложения, сайты в том же nginx, n8n и общий Postgres `postgres-shared` —
их не трогать. Перезагрузка висит в очереди после обновлений системы и делается только
с согласия хозяина. Как всё ставилось и почему — `deploy/README.md`.

- **Сайт** — `/srv/astvard`, клон ветки `valheim-mod`; служба `astvard-backend`
  запускает `node /srv/astvard/server.js`, nginx отдаёт всё на `:3001`. **База — своя
  роль и своя база `astvard_panel` внутри чужого контейнера `postgres-shared`**:
  подключение к ней закрыто для `PUBLIC`, пароль — в `/srv/astvard/.env` и больше
  нигде. Загрузки — `/srv/astvard/uploads`; они в `.gitignore` и переживают обновление,
  но не `git clean -xdf`, поэтому его здесь не запускать. Обновить — `git push`, потом
  на VPS `/srv/astvard/deploy/update-site.sh`: он сам откатится, если `/api/health` не
  ответит. Поменялся юнит systemd — запускать `install-site.sh`, обновление его не
  трогает. База `astvard` в том же контейнере осталась от прежнего портала — не нужна,
  но и не удалена.
- **Игровой сервер** — Docker-контейнер `astvard-valheim`, всё в `/srv/valheim`: игра в
  `server/`, мир и списки в `saves/`, лог игры `logs/server.log`, лог BepInEx и мода —
  `server/BepInEx/LogOutput.log`, настройки — `server.env`. Команды — из `/srv/astvard`
  через `docker compose -f deploy/valheim/compose.yml`.
- **Мир на VPS — копия `AstwardWorld`** с Windows-сервера, сохранение № 72 от 11.09.2026
  22:02. С этого момента миры разошлись. Туда же перенесены списки доступа, настройки
  мода и четыре общих шаблона; руны — нет, счёт на VPS начался с нуля.
- **Останавливать — только `stop`** (или `down`, `restart`): в compose стоит
  `stop_signal: SIGINT`. Проверено 11.09.2026: остановка за 3.9 с, код выхода 0,
  `World save (5/5) done`, сохранение № 73. `docker kill` и `docker rm -f` теряют всё
  после последнего автосохранения.
- **Мод на Linux работает** (`BEPINEX=yes` в `server.env`): BepInEx 5.4.23.3 через
  doorstop, `Loading [Jotunn 2.30.0]`, `Loading [AstvardServerMod 1.0.0]`,
  `Kept zones: ZoneSystem.PokeLocalZone bound.`, ни одной ошибки или предупреждения
  (12.09.2026). **Хозяин на него зашёл 12.09.2026**: вайтлист пропустил, мод выдал
  админку, панель и шаблоны работают — подробности ниже, в незакрытом.
- **`DllNotFoundException: libParty.so` в логе игры — не наша и не мешает.** Файл
  лежит как `valheim_server_Data/Plugins/libparty.so`, а игра просит `libParty.so`; на
  Linux регистр важен, и PlayFab Party не поднимается. Он нужен только `-crossplay`,
  которого у нас нет.
- **Обновление игры поверх разложенного BepInEx проверено — BepInEx цел** (18.09.2026,
  VPS с 1.0.12 на 1.0.15). `app_update 896660 validate` не тронул ни одного чужого файла:
  41 файл в `BepInEx/` и `doorstop_libs/` до и после, `libdoorstop_x64.so` на месте, DLL мода
  та же по хешу. После обновления `Loading [Jotunn 2.30.0]`, `Loading [AstvardServerMod
  1.1.0]`, ошибок нет.
- **Но SteamCMD может отказаться обновлять, не начав качать.** Трижды подряд:
  `Update state (0x3) reconfiguring` → `(0x0) unknown` → `Error! App '896660' state is 0x6
  after update job`, ноль байт скачано. Ни место (180 ГБ свободно), ни память (13 ГБ) ни при

- **Сетевая версия 1.0.15 осталась 40**, как у 1.0.12 и 1.0.14, так что клиент постарше
  подключается по-прежнему. Игру обновляет **отдельная команда**
  (`docker compose … run --rm valheim update`), а не перезапуск контейнера: от `restart` или
  `stop`/`up` игра не обновится сама, и сюрприза не будет.
- **Осталось непроверенным:** не тронет ли SteamCMD
  `validate` чужие файлы, не проверено: после первого такого обновления смотреть, на
  месте ли `BepInEx/` и `doorstop_libs/`, и строки `Loading [...]` в логе BepInEx.

## Вход через Steam и вайтлист

**Регистрации как формы в портале нет** (с 12.09.2026). Аккаунт заводится сам при
первом входе через Steam: на игровой сервер пускают по номеру, а не по почте, и
аккаунт без Steam не может ни попросить доступ, ни получить его. Прежняя форма
(почта, пароль, ФИО, тип аккаунта, honeypot и арифметическая капча) осталась от
учётной системы компании и заводила ровно такие пустые аккаунты — снесена вместе с
`/api/auth/register` и `client/register.html`; адрес страницы жив и ведёт на вход.
Переключатель «Принимать новых игроков» (`allow_registration`) теперь означает
именно это: выключен — незнакомый номер Steam аккаунта не заводит, уже заведённые
входят.

**Типа аккаунта у человека больше нет** (19.09.2026). От панели электриков осталось
деление на «Клиента» и «Сотрудника»: оно стояло выбором в форме пользователя, бейджем в
таблице и строкой в карточке, а вход через Steam молча заводил «клиента». На игровом
портале человек — игрок, и другого вида аккаунта нет: выбор убран, бейджи убраны,
`account_type` не читается из запроса ни при заведении, ни при правке, и ни один из трёх
путей заведения аккаунта (Steam, вписывание админом в вайтлист, первый суперадмин) его
больше не назначает. Колонка в базе в тот же день ушла вместе с разделом «Сотрудники»,
который на ней держался. Роли в панели заодно стали словами: «Игрок»,
«Администратор», «Суперадмин» вместо `User`, `Admin`, `Superadmin` и «Редактора»,
оставшегося от панели блога. Скрытые блоки кабинета «моя карточка сотрудника»,
«инструмент» и «авто» снесены тогда же.

Пароль при этом остался: он есть у аккаунтов, которые админ заводит в панели, и его
может задать себе любой игрок — в кабинете, в блоке «Дополнить аккаунт». Там же
меняются ник и почта. Правила ника живут в `src/nickname.js` и знают про «ё»;
текущий пароль спрашивается только у того, у кого он уже есть — иначе первый пароль
задать было бы нечем. Почта приводится к нижнему регистру при записи: иначе
`Ivan@mail.ru` и `ivan@mail.ru` — два аккаунта на один живой адрес.


В вайтлист ведут две дороги. **Обычная:** игрок жмёт «Войти через Steam»,
возвращается с подтверждённым `SteamID64`, отдельной кнопкой просит доступ — может
приложить пару слов о себе, — админка показывает заявку, админ решает. **Короткая:**
админ сам вписывает номер в админке, для тех, кто на сайт не заходил; запись сразу
одобрена, заявки не было. **Решение доезжает до сервера само** (с 12.09.2026): после каждой выдачи, отказа и
переключения админки сайт переписывает `permittedlist.txt` и `adminlist.txt` прямо
в папке сохранений, а игра перечитывает их секунд за десять. Запись — во временный
файл рядом и переименование: так получается и атомарность, и свежий mtime, без
которого `SyncedList.Load` файл игнорирует. Прежний файл остаётся рядом как `.bak`.
Кнопка «Применить на сервере» в админке делает то же самое руками — на случай,
когда файлы разъехались с базой. Кнопки «Собрать …» никуда не делись: они нужны,
когда сервер живёт не на этой машине. **Пустой `permittedlist.txt` не пишется
никогда** — для игры он означает «пускать всех».

**Приём заявок бывает автоматический**: переключатель «Принимать заявки на сервер
сразу» в настройках. Включён — заявка игрока сама становится одобренной и тут же
уезжает в файл, то есть человек может заходить через десяток секунд. Выключен —
как раньше, заявка ждёт админа.

Рядом, из той же таблицы, выдаётся **админка на игровом сервере** —
`adminlist.txt`. Это не то же самое, что роль на сайте: `role` — права в портале,
`server_admin` — права в игре, и совпадать они не обязаны.

В админке с 12.09.2026 две таблицы вместо одной: «Заявки» — то, на что надо ответить
сегодня, «Доступ на сервер» — **все, кто привязал Steam**, с их состоянием. Вторая
таблица держит и тех, кто ничего не просил: выдать доступ такому человеку — обычное
дело, а раньше до него можно было добраться только через поле «добавить по SteamID64».
Поэтому «Выдать доступ» идёт через `grantWhitelist` (ему нужен только `steam_id`), а
«Отклонить» — через `decideWhitelist`, который по-прежнему отказывается решать за того,
кто не спрашивал. **«Забрать доступ» возвращает строку в `none` и заодно снимает
`server_admin`**: права в игре и право войти — разные вещи, но админ, которому вход
закрыт, это право, о котором забудут, а пустой `permittedlist.txt` пускает всех —
именно в этот момент забытая строка в `adminlist.txt` и сработает.

**Steam говорит на OpenID 2.0, и ключ для этого не нужен.** Два перехода:
`/api/auth/steam` уводит к Steam, `/api/auth/steam/return` принимает ответ.

- **Ответ Steam — не доказательство, пока Steam его не подтвердил.** Всё приходит
  в адресной строке игрока, то есть это текст, который может написать кто угодно.
  Единственное, что делает его доказательством, — обратный запрос к Steam с
  `openid.mode=check_authentication` и строка `is_valid:true` в ответе. **Без этого
  шага любой желающий входит любым SteamID, введя URL руками.** Проверено 11.09.2026
  живьём: подделанный ответ с чужим номером Steam отверг, куку сайт не выдал.
- **Подпись покрывает только поля из `openid.signed`.** Ответ, где `claimed_id` вне
  этого списка, несёт номер, который выбрал отправитель, — а `check_authentication`
  на остальное всё равно ответит «годно». Поэтому список проверяется отдельно.
- **`return_to` сверяется с нашим адресом.** Он входит в подпись, и это то, что не
  даёт переиграть на нашем сайте ответ, выписанный для чужого.
- **Steam недоступен — значит «не вошёл».** Любая ошибка сети по пути к
  `check_authentication` обязана читаться как отказ, никогда как успех.
- **Ручной ввод номера убран совсем.** Пока он существовал, игрок мог вписать чужой
  `SteamID64`: занять его (колонка уникальна) и подвести админа к тому, чтобы доступ
  открыли не тому человеку. Теперь `steam_id` попадает на строку только из ответа
  Steam, и `/api/whitelist/request` тела больше не читает.
- **Аккаунт может не иметь ни email, ни пароля** — у пришедшего из Steam их взять
  негде. Обе колонки стали nullable, а `users_has_a_way_in` следит, чтобы у строки
  остался хоть один способ входа: пара email+пароль или `steam_id`.
- **Ник берётся из публичного XML профиля** (`/profiles/<id>/?xml=1`, ключ не нужен)
  при создании аккаунта — и ещё раз при входе, если в базе до сих пор стоит заглушка
  `Викинг <5 цифр>`. Это удобство, а не условие: приватный профиль или молчащий Steam
  оставляют заглушку, вход от этого не ломается. Второй заход за ником появился
  12.09.2026 после того, как сайт встретил хозяина как «Викинг 08760»: аккаунт заводит
  `src/bootstrap.js` при первом старте, и Steam в тот момент имени не дал, а потом
  спросить его было уже негде. Заменяется **только заглушка** — выбранное человеком имя
  не трогаем. Ники Steam проходят чистку от невидимых символов: имя из одних zero-width
  пробелов выглядело бы в списках пустым.
- **Третий заход — сам сайт, без игрока** (20.09.2026, `src/steamNames.js`). Оба прежних
  случая требуют, чтобы человек пришёл: завёл аккаунт или вошёл снова. Кто не пришёл,
  остаётся заглушкой — «Викинг 90066» простоял на боевом восемь дней, а Steam всё это
  время отдавал по тому номеру «Vallerii». Теперь при старте сайта и дальше раз в шесть
  часов все строки с заглушкой переспрашиваются заново, по одной с паузой; в админке на
  «Вайтлисте» та же перепроверка есть кнопкой «Обновить ники» — она нужна, чтобы не ждать
  шесть часов и чтобы **услышать ответ**: Steam молчит, имя занято другим аккаунтом или
  всё уже настоящее. Кто именно носит заглушку, решает `fallbackNickname` — та самая
  функция, которая её и выдаёт, а не похожий шаблон в SQL. Занятое имя — строка в логе, а
  не упавший обход. Проверено 20.09.2026: на стенде обход при старте переименовал
  заглушку живым запросом к Steam, кнопка ответила `renamed: Викинг 90066 → Vallerii`, на
  боевом после выкатки в логе `Ники из Steam: Викинг 90066 → Vallerii` и строка в базе
  стала «Vallerii».
- **`adminlist.txt` требует ДВЕ формы одного номера** — `V_<SteamID64>` и
  `Steam_<SteamID64>`, обе. `ZNet.PlayerIsAdmin` сравнивает id сырым, без
  `FilterPlatformUserID`, поэтому совпадает только с той формой, которую прислал
  клиент, то есть `Steam_…`; от этой проверки зависит кнопка кика в игровом списке
  игроков. Всё остальное, что читает список, идёт через `ListContainsId` и видит
  только `V_…`. Напишешь одну форму — часть прав молча не появится.
- **Пустой `adminlist.txt` безопасен, в отличие от пустого `permittedlist.txt`.**
  Он означает «админов нет», а не «админы все», поэтому выгрузка без записей
  отдаётся, а не отклоняется: снять права тоже надо уметь. Кнопка при этом
  предупреждает, что файл снимет админку со всех.
- **Админку в игре выдаёт только суперадмин.** Кто может её выдать — может выдать
  себе, а это спавн, бан и кик. Обычный админ сайта отвечает на заявки, но кнопок
  админки не видит и получил бы 403. С 12.09.2026 это явные кнопки «Дать админку» /
  «Забрать админку» в строке игрока (раньше была галочка «в игре», её не замечали), с
  подтверждением и тостом о том, записался ли список на сервер. **Дать** можно только
  тому, у кого есть доступ (сервер отвечает 409): админ, которого не пускают, — это
  право, которое сработает в день, когда список опустеет. **Забрать** — у любого, у
  кого она есть: такие забытые админы без доступа уже встречаются, и снимать их надо
  уметь.
- **Ручной ввод номера остался ровно в одном месте — у админа**, в форме «Добавить
  в вайтлист». Поэтому ответ возвращает никнейм из Steam, и админка его показывает:
  опечатка в номере всплывает как чужое имя, а не как тишина.
- **`steam_id_verified` отличает подтверждённый номер от вписанного руками.**
  Steam подписался — `true`; админ ввёл — `false`, и так и написано и в кабинете, и в
  таблице. Флаг переключается сам, когда владелец впервые входит через Steam:
  номер наконец приходит подписанным.
- **ID лежит в базе без префикса**, `V_` приписывается только при выгрузке
  (`src/steamId.js`). Почему годится ровно `V_<SteamID64>` — выше, в разделе
  про сервер.
- **SteamID64 нельзя пропускать через `Number`.** База индивидуальных аккаунтов
  76561197960265728 уже больше 2^53, и любой круг через float сдвигает последние
  цифры, то есть пускает соседний аккаунт. Разбор и границы считаются на `BigInt`,
  дальше id живёт строкой.
- **Выгрузка отказывается отдать файл без записей** — 409, а не пустой файл.
  Пустой `permittedlist.txt` означает «пускать всех», так что файл из нуля
  одобренных заявок открыл бы сервер всему интернету — ровно наоборот к тому,
  зачем его собирали.
- **Комментариев в выгружаемый файл не кладём.** Игра пишет их в свой файл сама и
  почти наверняка не считает записью — иначе её собственный свежий файл никого бы
  не пускал, — но на 1.0 это не проверялось, а ошибиться здесь значит снова
  открыть сервер. Дешевле не проверять, чем проверять собой.
- **Привязка другого Steam сбрасывает ответ по вайтлисту в `none`.** Прежнее решение
  было про прежний номер. Не в `pending`: попросить доступ — осознанное действие.
- Один Steam — один аккаунт: `steam_id` уникален. Залогиненный игрок, привязывающий
  чужой уже занятый номер, получает отказ, а не перехват аккаунта.

## Поиск и превью ссылок

**С 13.09.2026 публичные страницы собирает сервер** (`src/seo.js`), а не скрипт в
браузере. Раньше `client/app.js` после загрузки подставлял заголовок, тексты разделов и
статьи, и тот, кто скриптов не исполняет, — Яндекс через раз, Telegram, VK и Discord
никогда — видел заглушки панели: «О нашем блоге», «г. Вильнюс, ул. Разработчиков». А
вкладка называлась просто «Astvard»: `loadSettings` затирал `<title>` названием сайта.
Слова «Valheim» не было ни в заголовке, ни в описании. Всё это видно на боевом до
выкатки, 13.09.2026.

- **Сайт — не одна страница, а шесть** (19.09.2026). Было: одна главная с якорями, и
  каждая новая тема делала её длиннее — раздел нельзя было дать ссылкой, у него не было
  ни своего заголовка в выдаче, ни своего описания, а «Что умеет мод» раздул страницу до
  79 КБ. Стало: `/` (витрина и статус серверов), `/server` (руны и общие постройки),
  `/mod` (что умеет мод), `/join` (как попасть), `/news` (лента), `/about` (о проекте и
  контакты). Список страниц — `PAGES` в `src/seo.js`: адрес, кусок разметки, пункт меню,
  заголовок и описание для поиска; **добавить страницу — это строка там и файл в
  `src/templates/pages/`**, маршрут и карта сайта подхватят сами.
  - **Оболочка одна** — `src/templates/layout.html`: шапка, меню, подвал, скрипты.
    `{{{content}}}` — кусок страницы, `{{{nav}}}` — меню, `{{{scripts}}}` — скрипты именно
    этой страницы (ленте нечего оживлять). `client/index.html` больше нет.
  - **Кусок заполняется раньше оболочки**: подставленное значение второй раз не
    просматривается, иначе текст статьи с двойными скобками стал бы полем шаблона.
  - **Меню строит сервер**, с `active` и `aria-current` — подсветка нужна и тому, кто
    скриптов не исполняет, а ссылки ведут на адреса, а не на якоря.
  - **Один адрес на раздел**: `/mod/` уводит 301 на `/mod`, `/index.html` — на `/`.
    Старые ссылки с якорями (`/#mod`, `/#articles-section`) переводит `MOVED_SECTIONS` в
    `client/app.js` — их успели раздать в Discord.
  - **Проверка чужих адресов в CSP ходит и по `src/templates`** (тест в
    `test/http.test.js`): разметка публичных страниц теперь там, и новый внешний скрипт
    иначе прошёл бы мимо неё незамеченным.
  - **«Скачать мод» — кнопка в меню, на каждой странице** (19.09.2026), и по ней окно с
    выбором: архив с GitHub или менеджер модов. Адреса — те же настройки
    `mod_download_url` и `thunderstore_url`, что у кнопок на `/mod` и ссылок в подвале;
    **обе ссылки лежат в разметке**, скрипт только показывает окно, так что оно работает
    и при мёртвом API. Не задан ни один адрес — нет ни кнопки, ни окна: кнопка,
    открывающая пустое окно, хуже её отсутствия. Само окно теперь общее для сайта
    (`.site-modal`, было `.feature-modal` у плиток мода) — и плитки, и выбор открываются
    одним и тем же кодом.
- **Куски страниц — шаблоны.** `{{ключ}}` экранируется, `{{{ключ}}}` идёт как
  есть, незаполненный ключ остаётся в странице видимым. Тест проверяет, что в ответе
  нет ни одного `{{`, поэтому **двойных фигурных скобок в комментариях шаблона не
  писать** — на этом он упал в первый же прогон. Тексты — из настроек; пустая

## Постройки для игроков: сайт и мод вместе

**С 13.09.2026 правила для игроков и доступ к общим постройкам меняются и в игре, и на
сайте** («Админка → Постройки»). Раньше и то и другое жило только в моде: правила в его
конфиге, доступ — строкой `#players yes` в файле шаблона, а менять можно было только из
игровой панели. Теперь хранит сайт (`src/gameBuilds.js`, таблицы `game_build_rules`,
`game_build_rule_meta`, `game_template_access`, `game_build_sync`), а мод
(`Plugin.SiteBuilds.cs`) раз в `[Сайт] BuildsSeconds` (15 с) забирает состояние
`GET /api/game/builds?rev=N` по тому же токену, что и списки доступа, и отправляет
изменённое админом в игре `POST`-ом туда же. Адрес — `[Сайт] BuildsUrl`; пустой значит
«рядом со списками»: `ListsUrl`, где `lists` заменено на `builds`, так что серверу, который
уже забирает списки, новая строка в конфиге не нужна.

- **«Действует последнее» — это порядок, а не часы.** Каждое изменение с любой стороны
  берёт следующую ревизию из `game_build_sync`; мод передаёт в `rev` ревизию, которую уже
  применил, и строка с ревизией выше помечается в админке «ждёт сервер». Часы VPS,
  контейнера и браузера сверять не приходится.
- **Мод сначала отправляет, потом забирает.** Изменение из игры, которого сайт ещё не
  слышал, новее любого ответа сайта: применить ответ раньше — значит вернуть админу под
  руки старое значение. Пока очередь отправки не пуста, ответ сайта не применяется.
- **Первое знакомство — засев.** Пустой сайт отвечает `seed needed`, и мод присылает все
  свои правила и доступ из заголовков шаблонов. Засев только дописывает недостающее —
  правка, сделанная на сайте раньше, остаётся, — а второй засев игнорируется.
- **Какие правила бывают, сайт не знает сам.** Их при каждом старте описывает мод
  (`meta`: название, группа, вид, границы), и сайт проверяет значения по этим границам.
  Правило, добавленное в новой сборке мода, появляется в админке без правки сайта.
- **Доступ по имени — заголовок `#allow <SteamID64,…>`** в файле шаблона, рядом с
  `#players yes`. Сервер сверяет платформенный id сокета при каждой постройке
  (`OpenTo` в `Plugin.BuildPause.cs`), а список общих построек теперь собирается для
  каждого подключённого отдельно: игрок видит открытое ему, а чужие номера не уходят
  никому. «Разрешить игрокам» в игре трогает только «всем», выбранных оставляет;
  выбирать людей можно только на сайте. Публичная страница говорит «открыта некоторым
  игрокам» — сколько и кому, не говорит.
- **Файлы шаблонов пишет только мод**, и только когда заголовки меняются, через
  временный файл. Сайт папку конфигов мода по-прежнему лишь читает — прав на запись туда
  ему не нужно.
- **Проверено 13.09.2026 на отладочном сервере Windows с локальным сайтом**, живым
  обменом: засев (20 правил, 4 постройки); правка на сайте доехала за ~7 с — в конфиге
  `Floor = 0`, `CopyMax = 12`, пауза 3 мин, в «Плавильне» `#players yes` и `#allow`
  сразу после первой строки; «Не для всех» и снятая галочка в «Кому…» через интерфейс
  убрали оба заголовка; «ждёт сервер» сменилось на «применено» само. **Не проверено**:
  изменение из игры (нужен клиент) и постройка игроком, которому постройку открыли по
  имени.
- **На VPS включено 13.09.2026 в 21:27 UTC** сборкой `6bbd7dac`. Перезапуск ждал
  последнего игрока разовой службой `systemd-run` (лог без его выхода плюс живой
  UDP-трафик на 2456 — tcpdump показал ~230 пакетов в секунду от клиента, который по
  логу ещё «в игре»; остановка сразу после ухода, мир сохранён). Мод засеял сайт —
  20 правил ровно со значениями из конфига сервера и 3 постройки — и дальше спрашивает
  раз в 15 с (`GET /api/game/builds?rev=5` → 200 в журнале nginx), списки доступа — как
  раньше, раз в минуту. `BuildsUrl` в конфиге пуст и вывелся из `ListsUrl`. Хозяин за
  20 минут до подключения сервера уже нажимал «Открыть всем» / «Не для всех» у двух
  построек: засев эти правки оставил (`updated_by` — его ник, ревизии 2 и 4) и дописал
  только третью постройку; заголовки в файлах с этим уже совпадали, мод ничего не
  переписал. Публичная страница показывает то же.
- **Встроенных построек в моде больше нет** (14.09.2026). С 08.09 мод при каждом запуске
  записывал в папку шаблонов пять построек хозяина из `BuiltInTemplates.cs` («Стартовый
  дом №1», «Плавильня», «Угольные печи», «Полная кухня», «Платформа 4х4») — не только
  себе, а каждому, кто поставил мод. Хозяин заметил их у игроков в «Шаблонах»: при
  открытом «Копировании» и выключенных «Ресурсах с игроков» они ставились даром и без
  паузы. Теперь шаблон берётся только с сервера («Шаблоны сервера», открытые игроку) или из
  собственной папки игрока. Уже записанные у игроков файлы мод не трогает: это их папка,
  и отличить свой изменённый шаблон от посеянного честно нечем.
- **Локальный стенд без `VALHEIM_MOD_CONFIG` в `.env`** не видит файлы шаблонов и пишет у
  каждой постройки «сайт не видит файл» — это не сломанный обмен: кнопки работают,
  доступ хранится по имени. На отладочном сервере для обмена стоят `BuildsUrl` на
  `http://127.0.0.1:3001/api/game/builds` и `ListsToken`, а `ListsUrl` пуст — чтобы мод
  не переписывал локальные списки доступа данными локальной базы.

## Сборка и раскладка мода

DLL кладётся **в две папки**, и обе должны совпадать байт в байт. Разные версии
на клиенте и сервере дают тихие рассинхроны, которые выглядят как «кнопка не работает».

**С Thunderstore одинаковой DLL у всех больше не будет — и это выбор хозяина**
(16.09.2026). Игроки ставят мод из менеджера и обновляются когда захотят, а проверок,
которые не пускают на сервер, в моде нет намеренно: заходят и без мода, и со старой
версией. Правило «байт в байт» остаётся про наши три установки — клиент,
Windows-сервер и VPS. У игроков версия может быть любой, поэтому формат обмена обязан
терпеть старого клиента; если терпеть больше нельзя — это новая мажорная версия, и
только она. Расхождение при этом не молчит: сервер сообщает свою версию в ответ на
обычный запрос панели, клиент один раз за подключение пишет строку в чат. Версия живёт
одной константой `Version` в `Plugin.cs`, `manifest.json` обязан её повторять, а
пакет и правила — в `tools/thunderstore/README.md`.

```bash
dotnet build valheim-mod/AstvardServerMod/AstvardServerMod.csproj -c Release
```

Собранное лежит в `bin/Release/net472/` — **не в Debug**, туда никто не смотрит.
Копировать в обе:

- `C:\Games\steamapps\common\Valheim\BepInEx\plugins\`
- `C:\Games\steamapps\common\Valheim dedicated server\BepInEx\plugins\`

Сверять всегда хешем, а не датой:

```bash
md5sum valheim-mod/AstvardServerMod/bin/Release/net472/AstvardServerMod.dll \
       "/c/Games/steamapps/common/Valheim/BepInEx/plugins/AstvardServerMod.dll" \
       "/c/Games/steamapps/common/Valheim dedicated server/BepInEx/plugins/AstvardServerMod.dll"
```

Игру и сервер надо перезапускать — DLL читается один раз при старте.

`/srv/valheim/server/BepInEx/plugins/`. Клиент у хозяина один на оба сервера, так
что DLL на VPS должна совпадать с клиентской всякий раз, когда играют там. **С

Прежние сборки остаются на VPS в `/srv/valheim` как `AstvardServerMod.dll.<md5>.bak`:

**Раскладывает DLL одна сессия, и хозяин говорит какая** (19.09.2026). В этой папке
работают две, и обе собирали и копировали в одни и те же `BepInEx/plugins`, перетирая друг
друга: разложенное одной жило до первой сборки другой, а хеш в этих заметках устаревал
быстрее, чем его успевали записать. Поэтому раскладка и перезапуск отладочного сервера —
за той сессией, которой хозяин это сказал; остальные собирают у себя, коммитят и **в
игровые папки не копируют**. Если не помнишь, сказали ли это тебе, — значит не тебе:
спроси, а не раскладывай. Правило про чистое дерево выше от этого не отменяется, оно про
другое — про то, что попадает в сборку.

**Собирать для выкладки — только из чистого дерева** (19.09.2026). В этой папке иногда
работает вторая сессия, и `dotnet build` заберёт её незакоммиченные правки молча: 1.2.4,
собранная в 17:47, унесла в себе чужой `Plugin.ChestRow.cs`, правленный в 17:42, и на VPS
уехало бы то, чего нет в git. Поймалось сравнением времени файлов. Порядок: `git worktree
add <папка> <коммит>`, собрать там, сверить `md5sum` — сборка из дерева с чужими правками
даёт другой хеш, и это единственный признак.

**Но и хеш сам по себе — не доказательство совпадения исходников: он зависит от пути.**
Тот же код из `…/clean-build` дал `107a18a7`, а из `…/release-build` — `d155cf2b`:
компилятор пишет пути в сборку. Поэтому архив для релиза собирается **не заново, а из той
самой DLL, что разложена на серверах** — она копируется в `bin/Release` перед
`tools/release/build.py`. Иначе наружу уедет файл, которого никто не запускал, а заметка
«везде одно и то же» станет неправдой в тот же день.

**Раскладывать приходилось под запущенной игрой**, а Windows переписать открытый файл не
даёт — зато даёт переименовать. Отодвинутые так сборки лежат рядом, в тех же папках, как
`AstvardServerMod.locked-20260919b.bak`, `…-c.bak` и `…-d.bak` (последняя — `47f98f7f`,
отодвинута 1.2.6). Работающая игра при этом остаётся на
прежней сборке: DLL читается один раз при старте, и новая начинается с их следующего
запуска — на Windows-сервере это 19.09 в 17:45, на VPS в 14:59 UTC.
В этих же трёх папках лежит и сама `Jotunn.dll`, и её версия должна совпадать так же:
мод собирается против той, что лежит у **выделенного сервера** (`HintPath` в csproj), а
работает у клиента. Новую DLL — `scp` в эту папку, `chown valheim:valheim`,
`md5sum` там же, затем `docker compose -f deploy/valheim/compose.yml restart` из
`/srv/astvard` (restart останавливает тем же SIGINT, мир пишется).
Если на сервере могут играть, вместо `restart` — `deploy/valheim/restart-when-empty.sh`: DLL
кладётся рядом как `AstvardServerMod.dll.new`, скрипт ждёт, пока ни лог, ни порты не покажут
игроков, подменяет её, прежнюю оставляет в `/srv/valheim` как `.bak` и поднимает сервер; как
запускать — в его шапке, ход — в `/root/astvard-restart-status.txt`. **Запуск по строке
`Game server connected` вслепую не ждать:** пока новая игра не написала своё, в файле строки
прошлого запуска, и ожидание «дожидалось» сразу — так обманулись 13.09.2026. Скрипт сверяет
время строки с часами контейнера: в логе его местное время, не время машины.

Тесты геометрии игры не требуют и идут за секунды:

```bash
dotnet test valheim-mod/AstvardServerMod.Tests
```

Они компилируют `Geometry.cs` внутрь себя (`<Compile Include>`), а не ссылаются на
мод: мод собирается только там, где установлен Valheim, а тесты должны идти везде.
Поэтому **вся математика, которую хочется проверить, должна жить в `Geometry.cs`** —
файле, который не знает ни про Unity, ни про игру.

## Как здесь принято

- **Комментарии и коммиты — по-английски. Всё, что видит игрок, — по-русски.**
  Не смешивать. UI-строки в коде русские, комментарий рядом с ними английский.
- Комментарий объясняет **почему**, а не что. Строку, пересказывающую соседний код,
  лучше не писать.
- Сообщение коммита — обычная фраза без префиксов вроде `feat:`, а тело объясняет
  причину и чем это было раньше. Примеры в `git log`; держись той же интонации.
- Заканчивать коммит строкой `Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>`.
- **Кнопки и ссылки — классами панели, а не своими.** Прежняя система
  (`.btn`/`.link-*` в `frontend/style.css`) уехала вместе со старым сайтом. У панели
  свои: `.btn` (она же основная), `.btn-secondary`, `.btn-danger`, `.btn-sm` для кнопок
  в строке таблицы, `.btn-save` в кабинете, `.badge`/`.badge-success`/`-warning`/
  `-danger`/`-muted` для статусов, `.data-table` у таблиц, `.card` в кабинете,
  `.check-chip` для галочки размером с палец, `.toolbar-form` для формы над таблицей.
  Смотреть соседний раздел и брать оттуда; новый вид — вариант в общих стилях, а не
  правило под один id. `.btn-primary` не существует: основная кнопка — это `.btn`.
- **Таблица на телефоне — это карточка, и класса `cards-mobile` мало.** Механизм
  держится на трёх вещах сразу: класс на таблице, разметка ячеек (`mobile-primary` —
  то, по чему строку узнают, `mobile-hidden` — что прячется, `no-label` — колонка
  действий, `empty-state` — заглушка) и тап по строке, открывающий полную строку в
  общей модалке `showRowDetail(заголовок, [[метка, значение]], кнопки)`. Поставишь
  только класс — на ≤640 px шапка исчезнет, строка станет flex-карточкой, а
  непомеченные ячейки уедут за край без полосы прокрутки: `.table-container` режет
  молча, а `.table-scroll` на этой ширине отключает прокрутку сам. На этом обожглись
  12.09.2026: на телефоне нельзя было ни одобрить заявку, ни удалить сервер, и
  выглядело всё целым. Кнопки, спрятанные вместе с `no-label`, обязаны появляться в
  футере модалки — те же классы, тот же делегированный обработчик.
- Работа идёт в ветке `valheim-mod`, не в `main`.
- **Правки делаются здесь и уезжают через GitHub. На VPS не коммитить и не править
  файлы репозитория.** Порядок один: правка на машине → коммит → `git push` →
  `/srv/astvard/deploy/update-site.sh` на VPS. Обновление делает `git reset --hard
  origin/valheim-mod`, то есть любая правка, сделанная на сервере, пропадёт молча и в
  самый неудобный момент — а «на проде поправлю и потом перенесу» так и не переносится.
  Вне git на VPS живут только `.env`, `deploy/valheim/.env` и `node_modules`.

## Грабли этого окружения

Не project-specific, но каждая из них однажды дала молчаливо неверный результат.

- **Кириллица в `curl -d '...'` портится.** Аргумент командной строки до curl доходит
  битым. Класть тело в файл и слать `--data-binary @file`. (Через heredoc в файл
  кириллица проходит нормально — проверено, UTF-8 не ломается.)
- **`taskkill` внутри составной команды Bash может «успешно» ничего не сделать.**
  Убивать процессы через PowerShell и обязательно проверять, что процесса больше нет,
  прежде чем измерять что-либо после.
- **`strings` в Git Bash отсутствует.** Поиск по бинарнику молча вернёт пустоту,
  как будто ничего не нашлось. Искать питоном.
- **Экранирование в heredoc и `re.sub` регулярно съедает правки:** `\n` превращается
  в настоящий перенос, замена переинтерпретируется. Для скриптовых правок — `chr(92)+"n"`
  и функция-замена вместо строки; лучше же писать файл целиком. Кавычки у `<<'EOF'` не
  спасают: 11.09.2026 `\\n` в питоне из такого heredoc всё равно дошёл переносом и
  разорвал строковые литералы C#. Скрипт с экранированием — только файлом через Write.
- **`grep` в Git Bash не годится для поиска `\r`, и врёт в обе стороны.** 11.09.2026
  `grep -c $'\r'` насчитал CR в каждой строке файлов, где их не было ни одного, а в
  трубе `printf 'a\r\nb\n' | grep -c "$(printf '\r')"` не нашёл настоящий. Концы строк
  проверять питоном: `open(f, 'rb').read().count(b'\r\n')`.
- **Из worktree `preview_start` всё равно берёт `.claude/launch.json` основной папки**
  и запускает её код, а не код worktree. 11.09.2026 сайт ответил 404 на маршрут, который
  был только в новой ветке. Что запущено нужное — проверять маршрутом, которого в старом
  коде нет; для кода из worktree нужна запись с абсолютными путями в основном
  `launch.json`, которую потом убрать. 14.09.2026 было уже наоборот: правку основного
  `.claude/` инструменты из worktree-сессии не дали, а запись во **временном** `launch.json`
  самой worktree (`node --env-file=<файл с PORT=3002> <абсолютный путь>/server.js`, чтобы
  не мешать чужому серверу на 3001) `preview_start` подхватил. Какой код отвечает — всё равно
  сверять заголовком или маршрутом, а запись убрать до коммита.
- **Длинный многострочный якорь может не совпасть, хотя он в файле есть.** 12.09.2026
  замена блока README с ``` и обратным слэшем внутри дала `count == 0`, при том что
  каждый его кусок по отдельности находился ровно один раз. Не гадать: искать границы
  блока по строкам (`startswith`, номер строки) и менять срез списка строк.
- **Правки «по якорю» проверяй счётчиком совпадений.** Однажды `replace(..., 1)` попал
  во второе совпадение и засунул создание кнопок внутрь обработчика клика — кнопки
  начали размножаться при каждом нажатии. Правило: `assert src.count(old) == 1`.
- **Труба из Node в Python на этой машине портит UTF-8.** 12.09.2026 ответ API,
  пропущенный через `node ... | python -c "json.load(sys.stdin)"`, вышел в
  «РџР»Р°РІРёР»СЊРЅСЏ»: питон читает stdin в cp1251. Данные были целы — врал замер.
  Проверять содержимое так: `curl -o файл`, затем `io.open(файл, encoding='utf-8')`.
- **Замер вёрстки сразу после смены вьюпорта врёт.** 12.09.2026: после
  `resize_window` без перезагрузки у уже отрисованных элементов каскад не
  пересчитался, и поле показало 120 px вместо 278 — почти записали в баги. А при
  скрытой панели предпросмотра кадры не идут, и CSS-переход замирает на начальном
  значении: модалка «висела» на 20 px ниже, хотя правило ставит `translateY(0)`.
  Правило: после смены ширины — перезагрузка, а геометрию мерить, погасив переходы.
- **Браузерная панель одна на всех.** Подагенты ходят в тот же Browser pane: пока
  они работают, вкладка может увести на чужой localhost, и `javascript_tool`
  выполнится не там, где ты думаешь. 12.09.2026 запрос ушёл на 8177 (стенд агента)
  вместо 3001 и вернул 501 от питоновского сервера. Проверять origin в ответе.
- Мод и сайт проверяй **эмпирически**. Живой запрос, живой сокет, живой лог. Слишком
  многое здесь выглядит рабочим и не работает.


## Раскладка сортировщика: сайт и мод

**С 19.09.2026 куда сортировщик кладёт предмет, решает админ на сайте** («Админка →
Сортировка», `src/gameSorting.js`, `Plugin.SiteSorting.cs`). Мод раскладывает по типу
предмета, и для большинства вещей этого хватает, но тип — слово игры, а не хозяина базы:
оленья шкура для игры такой же «материал», как камень.

- **Каталог присылает мод**, при каждом старте сервера: ключ перевода (`$item_deerhide`),
  русское имя, тип и та категория, которую мод дал бы сам. Сайт этого списка не знает и
  знать не должен — предметы новой версии игры появятся на странице без единой правки
  сайта. Тот же приём, что у правил построек (`game_build_rule_meta`).
- **Обратно уезжает только выбранное** — «ключ=номер», по строке. Четыреста строк «этот
  предмет там, где и был» — это килобайт в минуту без единого решения.
- **Пустой выбор — не «Разное».** Это «решает мод», то есть по типу предмета; «Разное» —
  ответ, пустой выбор — его отсутствие. В базе это `NULL` против `0`, и путать их значит
  молча менять раскладку на всей базе.
- **Дальше сервер раздаёт выбранное клиентам** (`AstvardSortKinds`), потому что сортировщик
  работает у них; токен сайта есть только у сервера. Раздача едет на том же обходе пиров,
  что и зоны, и только когда изменилось.
- Адрес выводится из `ListsUrl`, как у построек: `[Сайт] SortingUrl` пуст — значит
  `lists` → `sorting`, тем же токеном. Раз в минуту (`SortingSeconds`).
- Таблицы — `game_sort_items` и `game_sort_sync`; страница обновляется сама раз в десять
  секунд, пока открыта, как «Постройки».
- **Проверено живыми запросами на локальном стенде** (19.09.2026): пустой сайт отвечает
  `seed needed`, каталог принимается (`ok 3`), выбор поднимает ревизию, мод получает
  `rev 1` и строку выбора, снятие выбора убирает её, чужая категория и незнакомый предмет
  отклоняются, запрос без токена — 401. С 19.09 это ещё и два теста в `test/http.test.js`,
  включая то, что каталог от мода не стирает выбор админа. **Не проверено**: весь мод
  целиком — ни каталог из игры, ни раздача клиентам в игре не запускались ни разу.

**Страница «Сортировка» рассчитана на тысячу строк** (19.09.2026). На боевом в каталоге
982 предмета, и первая её версия — плоская таблица со списком у каждой строки — была
нерабочей: выбрано за все дни ноль. Что изменилось:

- **Полки над таблицей — перепись и фильтр разом.** Число на полке считается по итогу
  (выбор админа, а где его нет — решение мода по типу), потому что стену сундуков готовят
  под итог. Сразу видно перекос: «Оружие 238» и «Инструменты 10». Нажатие оставляет в
  таблице одну полку, повторное снимает фильтр.
- **Пачкой, одним запросом и одной ревизией** (`PATCH /api/admin/sorting/items`): отметить
  найденное, выбрать полку, подтвердить. Тридцать ревизий подряд значат для мода ровно то
  же, что одна, — он забирает выбор целиком, — зато «ждёт сервер» гаснет разом. Незнакомый
  ключ пропускается молча, в ответе — сколько строк легло.
- **Фильтры:** «решает сервер / выбрано руками» и тип предмета игры; поиск ищет и по типу.
  Перевод типов (`SORTING_TYPES` в `public/astvard.js`) — только для выпадающего списка, и
  незнакомый тип показывается как есть: новая версия игры добавит строку без перевода, а
  не сломает страницу. Сверялся он по самим предметам с боевого, а не по памяти.
- **Кто и когда выбрал** — эти поля приходили с сервера и выбрасывались страницей.
- **На телефоне — карточки**, как в остальных таблицах. Галочка остаётся видимой (иначе
  пачку не собрать), полка уходит подписью под имя, а полка-колонка и список прячутся: у
  ячейки «Сейчас» нет сжатия, и имени доставалось 46 px из 317. Список полок открывается
  тапом по карточке, в модалке.
- **После сохранения перерисовывается одна строка**, а не тысяча, и поиск ждёт 150 мс
  после последней буквы.
- **Смотреть панель, не входя в неё, можно стендом**: та же разметка из `public/index.html`
  и тот же кусок `public/astvard.js`, вокруг — заглушки `escapeHtml`, `showToast`,
  `confirmDialog` и подменённый `fetch` с поддельным каталогом. Стенд кладётся в папку
  черновиков и отдаётся `python -m http.server`: из `file://` браузерная панель работать не
  даёт («static snapshot»), а `.app-container` — сетка в две колонки, и без пустого
  `<aside class="sidebar">` страница встаёт в колонку 260 px и выглядит сломанной. Так
  найден и разобранный выше промах с шириной имени. **Живьём, с настоящим входом в
  панель, страницу по-прежнему не видели.**

**Постройку можно настроить и убрать с сайта** (19.09.2026). В «Админке → Постройки» у
каждой постройки появилась кнопка «Настроить»: имя, категория и «Убрать постройку» с
подтверждением. Сам сайт при этом по-прежнему **ничего не пишет** в папку мода — прав у
него там нет и не будет.

- **Просьба едет поручением с номером** (`game_build_jobs`): `job<TAB>id<TAB>вид<TAB>имя<TAB>значение`
  в том же ответе, что и правила с доступом. Мод делает и возвращает `done<TAB>id` своим

**Разбор мода 19.09.2026: что нашлось и что из этого починено.**

- **Повозку нельзя было назначить ни на подачу, ни на сбор** — и молча. `HasChestFlag` в
  `Plugin.Automation.cs` спрашивал `container.GetComponent<ZNetView>()`, а у повозки
  `Container` на дочернем объекте и `ZNetView` на корне; ровно та яма, что однажды
  оставила повозку неразобранной у сортировщика. Заметка об этом в списке была, а код —
  нет. Теперь везде `ViewOf` (вверх по объекту).
- **Два обращения к владельцу сети шли без проверки на null** (`TryStoreNearby`,
  `TakeFrom`): сегодня туда не попасть — повозка не проходила пометку, — но стоило
  починить пометку, и первое же исключение унесло бы **всю автоматику до конца сессии**.
  Починены вместе, иначе одно чинило бы во второе.
- **Поиск сундука в детали делался тысячами раз в секунду.** `GetComponentInChildren<Container>()`
  — рекурсивный обход префаба, а звали его трижды: автоматика раз в секунду, сортировщик
  раз в секунду, подписи дважды. На базе в полторы тысячи деталей это порядка шести тысяч
  обходов в секунду, и почти все — чтобы узнать, что контейнера нет. Теперь ответ помнится
  на деталь (`ContainerOf`), в том числе ответ «нет»; словарь чистится от снесённых
  деталей, когда перевалит за 4096 — зоны грузятся и выгружаются весь вечер.
- **Контур зоны сундуков считался каждый кадр**: 72 точки, у каждой спрошена высота земли,
  то есть больше четырёх тысяч запросов к физике в секунду, пока подсветка просто включена.
  Теперь — когда игрок отошёл на треть метра или поменял саму зону. У контура поставленной
  зоны такая же защита была с самого начала.
- **Любой сбой внутри посекундного прохода уносил работу до конца сессии.** Это не
  предположение: так мод уже терял автоматику, когда контракт RPC разъехался с игрой.
  Оба цикла — сортировщика и автоматики — теперь ловят исключение, жалуются **один раз на
  причину** и идут дальше. И то и другое ожидание (`WaitForSeconds`) заводится один раз, а
  не заново каждую секунду.
- **Ник с «|» или «=» рвал список имён** в зонах: строка имён разделена именно ими, а ник
  в Steam бывает любым. Чистится при отправке.

Что посмотрено и **оставлено как есть**: у `Plugin.Zones.cs` (серверные зоны) все списки
статические, мусора не делает; `Plan.Where` заводит список на предмет, но зовётся считанные

игроков это десяток мелких строк, мерить нечего. LINQ в горячих местах нет ни одного.

**Чего разбор не касался:** `Plugin.Terrain.cs`, `Plugin.RoadJob.cs`, `Plugin.Bridge.cs`,

  **Раскладка нигде не хранится и считается заново каждый проход**, отсюда всё остальное
  задаром: куча, переросшая порог, получает сундук сама; истраченная — сундук отдаёт, и он
  возвращается в общий котёл; что лежит не там, переносится (`TidyBins`), иначе дерево так и
  осталось бы в общем сундуке, а свой стоял бы рядом пустым. Чтобы решение не скакало,
  сундук под кучу выбирается по тому, **чего в нём уже больше** — перенос туда же это только
  усиливает, — а равные разрешаются порядком сундуков **по координатам**, а не по тому, в
  каком порядке их вернул обход. `OwnChestSlots = 0` возвращает прежнее поведение. 16 тестов,
  включая пример хозяина: 500 дерева, 200 камня, 300 слитков, 30 меди, 2 олова и четыре
  сундука — три кучи разъезжаются по своим, руда ложится в четвёртый. **В игре не проверено.**

- **Уголь «пропадал» двумя дорогами, и обе настоящие** (19.09.2026, 1.2.7). Хозяин
  заметил, что уголь девается, когда сортировщик включён, и связал это с тем, что рядом

    кухня жжёт уголь и пустой — там это расход, а не оседание.
